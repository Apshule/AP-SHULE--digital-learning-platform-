PART B: AUTO-DISBURSEMENT PIPELINE
═══════════════════════════════════════════════════════════════

After an IPN confirms a successful client payment, automatically 
disburse to the institution.

FLOW:
1. IPN received → transaction marked completed
2. Calculate:
   - Fee = amount * (institution.service_fee_percentage / 100)
   - Net = amount - fee
3. Look up institution_beneficiaries by institutionId
4. If beneficiary exists AND isActive:
   - Call disbursement function
5. If no beneficiary OR beneficiary inactive:
   - Hold funds in AppShule account
   - Notify Super Admin: "Disbursement blocked — no beneficiary"
   - Status: transaction = completed, disbursement = pending

DISBURSEMENT FUNCTION (backend):
1. Build Yo! XML request based on beneficiary type:

TYPE A — Yo! Account (internal transfer):
<?xml version="1.0" encoding="UTF-8"?>
<AutoCreate>
  <Request>
    <APIUsername>{YO_API_USERNAME}</APIUsername>
    <APIpassword>{YO_API_PASSWORD}</APIPassword>
    <Method>acinternaltransfer</Method>
    <CurrencyCode>UGX</CurrencyCode>
    <Amount>{net}</Amount>
    <BeneficiaryAccount>{institutionYoAccount}</BeneficiaryAccount>
    <BeneficiaryEmail>{institutionEmail}</BeneficiaryEmail>
    <Narrative>Payment disbursement {reference}</Narrative>
    <ExternalReference>DISC-{reference}</ExternalReference>
  </Request>
</AutoCreate>

TYPE B — Mobile Money (acwithdrawfunds):
- Requires RSA signature (see Yo! docs Part 4.1)
- Include PublicKeyAuthenticationNonce + Signature
- Same structure as above but Method = acwithdrawfunds

TYPE C — Bank Account (acwithdrawfundstobank):
- Requires RSA signature
- Include BankAccountName, BankAccountNumber, 
  BankAccountIdentifier
- TransferTransactionType = EFT or RTGS

2. Send request to Yo! API
3. Yo! returns:
   - Success → yoTransactionId, settlement identifier
   - Error → error code + message
   - Pending → wait for webhook

4. Create payment_disbursements doc:
   - status = pending (initial) or completed
   - Store yoTransactionId

5. If success: notify institution "Funds sent"
6. If pending: wait for disbursement webhook (Part C)
7. If failed: 
   - Retry up to 3 times
   - After 3 failures: alert Super Admin
   - Hold funds in master account

RETRY LOGIC:
- Exponential backoff: 30s, 2min, 10min
- Log each attempt
- After 3 failures, mark as "needs_manual_review"

PART D: PARTIAL PAYMENTS ACROSS SECTORS
═══════════════════════════════════════════════════════════════

After each successful payment, update the appropriate sector record.

SECTOR 1 — Education (school_fees):
- Find school_fees doc by billReference
- Update:
  * amount_paid += payment amount
  * balance_remaining -= payment amount
  * payment_status = Paid / Partially Paid / Overpaid
  * last_payment_date = now

SECTOR 2 — MFI (microfinance_loans):
- Find loan by billReference
- Update:
  * amount_paid += payment amount
  * balance_remaining -= payment amount
  * repayment_status = On Track / Partially Paid / Fully Repaid / Overdue
  * last_payment_date = now
- If loan is in repayment schedule mode:
  * Find next pending installment
  * Mark it paid (or partially paid)
  * Advance to next installment

SECTOR 3 — Clinic (clinic_billing):
- Find bill by billReference
- Update:
  * amount_paid += payment amount
  * balance_remaining -= payment amount
  * payment_status = Paid / Partial / Unpaid
  * last_payment_date = now

UNIFIED UPDATE FUNCTION:
Add function updateSectorBalance(sector, referenceId, paymentAmount):
1. Switch based on sector
2. Get the sector doc
3. Update amounts + status
4. Write to sector_balances for unified view
5. Return updated status

PART E: OVERPAYMENT + CREDIT NOTES
═══════════════════════════════════════════════════════════════

When a client pays MORE than the balance:

EXAMPLE:
- Bill total: UGX 300,000
- Already paid: UGX 250,000
- Balance: UGX 50,000
- Client pays: UGX 80,000
- Overpayment: UGX 30,000

AUTOMATIC FLOW:
1. Bill balance = 0 → status = "Paid"
2. Create credit_notes doc:
   - creditAmount = 30,000
   - balanceRemaining = 30,000
   - status = active
   - expiryDate = +12 months
3. Notify client:
   "You overpaid UGX 30,000. A credit note has been created. 
    It will apply to your next bill."
4. Notify institution: "Overpayment received"
5. Notify Super Admin

CREDIT NOTE APPLICATION:
When client has a new bill, system checks for active credit notes:
1. Find credit_notes WHERE clientId == current user AND 
   status == active AND balanceRemaining > 0
2. If found, apply automatically:
   - Reduce new bill by credit note amount
   - Update credit note: usedAmount += applied, 
     balanceRemaining -= applied
   - If balanceRemaining == 0: status = "used"
3. Notify client: "Your credit note of UGX X was applied to this bill"

MANUAL CREDIT APPLICATION:
- Client can also choose to apply credit at payment time
- Show available credits in payment modal:
  "You have UGX 30,000 credit available. Apply? [Yes] [No]"
